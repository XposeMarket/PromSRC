# Issue Triage and Tickets

Two related jobs: (A) moving incoming issues to a clear state with an actionable brief, and (B) turning approved work into small, independently shippable tickets. All tracker access uses `connector_github_*` tools; the gh CLI is not installed. Every tracker write (comment, label, close, create) needs the user's approval in the moment unless they already authorized that exact action. Prometheus source issues live in `XposeMarket/PromSRC`.

## Label model

- Category (exactly one): `bug`, `enhancement`.
- State (exactly one): `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`.
- Map these canonical roles to the repo's real label strings once (check `GET /repos/{o}/{r}/labels` via `connector_github_api_request`) and save the mapping in `plans/<repo>-triage-labels.md`. If labels conflict on an issue, ask before changing anything.
- Every comment posted during triage starts with: `> Generated by AI (Prometheus) during triage.`

## A. Triage

### Show what needs attention
`connector_github_list_issues` (and `connector_github_list_prs` if external PRs are in scope; external means not a collaborator). Present three buckets, oldest first, with counts and one line each: unlabeled; `needs-triage`; `needs-info` with reporter activity since the last triage note. Tag lines `[issue]` or `[PR]`. Let the user pick via a card.

### Triage one item
1. **Gather**: body, comments, labels, author, dates; for a PR, the diff (`connector_github_get_pr` plus `connector_github_api_request` for files). Parse prior triage notes so resolved questions are not re-asked.
2. **Redundancy and prior rejection**: search the code by domain concept, not just the issue's wording (one multi-pattern `workspace_read(action:"grep")`), and report where you looked. Check `.out-of-scope/` notes if the repo keeps them.
3. **Recommend**: category, state, reasoning, and a short code summary (including "already implemented" if so). Send a card with your recommendation first and wait.
4. **Verify the claim**: reproduce a bug from the reporter's steps (`workspace_run`), or check out and test a PR. Report confirmed (with code path), failed, or insufficient detail.
5. **Grill if needed**: if the request is underspecified, run `requirements-grilling` to shape it.
6. **Apply the outcome** (after approval):
   - `ready-for-agent`: post an agent brief comment (template below).
   - `ready-for-human`: same brief, plus why it cannot be delegated (judgment, access, design, manual testing).
   - `needs-info`: post triage notes: "What we've established" and "What we still need from you" with specific, answerable questions.
   - `wontfix`: already implemented (point to where; do not record as rejected), rejected bug (polite reason), or rejected enhancement (record the reasoning in `.out-of-scope/<topic>.md` if the repo uses it, link it, close).
   Use `connector_github_update_issue` for labels and state, `connector_github_comment` for comments.
A direct "move #42 to X" from the user is an override: confirm the exact actions, then apply, skipping grilling.

### Agent brief template (durable, behavioral)
```
## Agent Brief
Category: bug | enhancement
Summary: one line
Current behavior: ...
Desired behavior: ... (edge cases and error conditions)
Key interfaces: types, function signatures, config shapes to look for or change
Acceptance criteria: - [ ] specific, independently testable items
Out of scope: adjacent things not to touch
```
Describe interfaces and behavior, never file paths or line numbers (they go stale), and never step-by-step implementation.

## B. Spec or plan to tickets

1. Read the source (spec file, plan file, issue via `connector_github_get_pr`/`list_issues`, or the conversation). Explore the code if not already done; look for a prefactor that makes the work easier and schedule it first.
2. Draft **tracer-bullet** tickets: each is a narrow but complete vertical slice through every layer it needs (schema, API, UI, tests), demoable or verifiable alone, small enough for one fresh context. Give each its blocking edges.
3. Exception for wide mechanical refactors (renames, retypes across the codebase): sequence as expand (add the new form beside the old), migrate in batches sized by blast radius (one ticket per batch, each blocked by the expand), then contract (remove the old form).
4. Show the numbered breakdown (title, blocked by, what it delivers) and ask via `ask_prometheus_questions`: granularity (`Recommended: about right` / too coarse / too fine), whether the edges are correct, and merges or splits. Iterate until approved.
5. Publish in dependency order, blockers first, so edges can reference real numbers:
   - GitHub: `connector_github_create_issue` per ticket with sections Parent, What to build, Acceptance criteria, Blocked by; label `ready-for-agent` unless told otherwise. Do not close or edit the parent issue.
   - Local: `plans/<feature-slug>/tickets/NN-<slug>.md`, one file per ticket with What to build, Blocked by, Status, and acceptance checkboxes.
6. The frontier is every ticket whose blockers are done; `implementation-plan-execution` can consume it.

## Exit criteria

Each triaged item has exactly one category and one state with the right artifact posted; each ticket set is approved, published in dependency order, and its frontier is stated. Record a `write_note` of what changed.
