## Attribution and changes

- `src/gateway/tasks/task-runner.ts:670-713`: before each bg event carried `task`, `prompt`, `taskPrompt` (e.g. **5,850B each**), a 12,463B output chunk both top-level and nested `data`, plus sometimes object-valued `event`. Now a typed string `event`, one bounded copy, initial task preview (1KiB) only, no duplicate nested data or repeated prompt. Event full detail stays accessible at `GET /api/background/:id/stream?after=<seq>` (`src/gateway/routes/tasks.router.ts:557`). `user_message` also gets explicit typed event at task-runner.ts:1362. Existing desktop/mobile handlers accept top-level fields and `eventType`, and use `bgId`/parent `sessionId`; no UI rewrite was needed.
- `src/gateway/process/supervisor.ts:840-867`: every output frame previously embedded full mutable run record (4KiB outputPreview, shellCommand, command) as well as the new chunk. Now output frames carry a small run identity and chunk; lifecycle frames preserve state/exit fields but exclude shellCommand and large workspace changes and bound previews. Full run and complete logs remain at `GET /api/processes/:runId` and `/log`. Existing desktop/mobile terminal reducers use `runId`, `sessionId`, `toolCallId`, `state`, `outputSeq`, `chunk`, and `sequence`; focused output still arrives in order. Output batches no longer call synchronous temp-write + rename in `ProcessRunStore`; async log appends were already in place and terminal record writes remain durable.
- `src/gateway/comms/broadcaster.ts:564-623`: focus opt-in previously filtered only selected main-chat events. Now unfocused bg progress and process output emit at most **one `session_activity` summary per second per session and client**, avoiding stringification when no client wants full frames. `process_run_started`/`update`/`exited`, bg status/final/error/done, and other structural events always go through; the 1MiB backlog filter discards only progress. Clients without focus opt-in keep legacy delivery. Fanout regression explicitly tests error/done/exited delivery and multi-session traffic.
- `src/gateway/core/server.ts:50-66,410-420,486,772`: raw `/api/status` hot path synchronously read/parses `model-runtime-status.json` and traverses `gatewayQueues` diagnostic callbacks every request. Now runtime file reads are async and cache last-known status; queue snapshot cached 500ms. WS command `broadcastPayload` JSON-serializes once instead of per client. Remaining status JSON serialization and occasional queue refresh still run on event loop.
- `electron/main.js:2237-2302`: the second `server-v2` was **intentional warm handoff**, not a spawn/restart race. Log: “Gateway 9684 is handing off ... it keeps 3 runtime(s) running while the replacement starts”; later “Warm handoff complete ... 9684 continues draining”. Startup rotates backend port, swaps relay only when healthy, and leaves old gateway alive until active threads drain. Do not kill or change that process model: the extra memory/CPU during lengthy drain is real but protecting in-flight work. No Electron fix warranted.
- `src/gateway/tasks/task-runner.ts:981-1023`: 1.2s background trace checkpoints copy session history and up to 500 process/live trace entries; a potential residual main-thread CPU cost not changed here because altering persistence semantics while live work runs needs a separate targeted regression.
